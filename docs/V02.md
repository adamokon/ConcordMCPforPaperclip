# v0.2: finish the receipt loop

The useful next step was completing one bounded task reliably. More agents and
a second scheduler would not solve lost results, expired readiness observations
or ambiguous execution. Paperclip remains the only model execution authority.

## Actual path

1. MCP records an idempotent scoped task and asks the native Paperclip coordinator
   to process it. A dedicated SSH key starts only MCP, under the service UID.
2. Before dispatch, the coordinator obtains a fresh trusted probe through a
   different forced-command SSH identity. It checks platform status, Process
   adapter, active runs, enrollment, credential-file metadata and Job/pod state.
   Presence of OAuth does not mean a fresh provider login; auth/quota stay unknown.
3. Paperclip executes the existing worker adapter. The bridge does not invoke
   worker RPC or give a model its persistent coordinator key.
4. A receive-only service looks up the exact journal task, project, assignee and
   native run. Missing, ambiguous or nonterminal evidence prevents acceptance.
   It waits for the exact run's Job/pods to disappear before receiving files.
5. A fixed worker helper snapshots only exact allowlisted files under that run's
   workspace. It rejects symlinks, hardlinks, special files, mutation during read,
   oversized files and some common secret forms. Raw logs and profile homes are
   never receipt artifacts. Secret-pattern checks are not comprehensive DLP.
6. The receiver copies verified Python files into an immutable ConfigMap and
   runs independent unittest discovery in a separate namespace, as UID65532,
   without OAuth, a PVC, service-account token, host mounts or service-link env.
   The root filesystem is read-only; temporary storage and resources are bounded.
7. NetworkPolicy denies ingress/egress. A node-installed, content-addressed
   **seccomp profile also blocks networking and io_uring** before test execution.
   Acceptance testing found that NetworkPolicy alone could allow an early packet;
   it is not the sole network boundary. Missing seccomp profiles fail pod creation.
8. Both sender and receiver verify content hashes and task/issue/agent/run binding.
   Test evidence is tied to the full manifest digest. The journal enters
   `review_ready`; only explicit operator review can queue final Paperclip Done.

## Batch questions and cooperation

`bridge_question.json` is a reserved protocol sidecar, not a repository file
claim. A successful question batch may omit unfinished output files. The receiver
records its question atomically with the verified snapshot, using an idempotent
run-derived message ID. A question-only batch gets protocol validation in the
sandbox; it is explicitly **not** a passing code test suite.

The coordinator records an answer and creates a bounded child with the exact
verified partial files and linked Q&A. The sidecar itself is omitted from child
source inputs. Parent execution must be parked, scopes cannot grow and an
unfinished child blocks parent acceptance. Messages never claim delivery to a
running model. Arbitrary agent-to-agent shell execution and automatic merging
are absent. Concord continues to offer the optional real MCP metadata view.

## Trust and deployment

The privileged host gateway is deliberately small. Its public input is only
`probe` or `receive(task UUID)`. Commands, containers, profiles, paths and sandbox
policy come from administrator-owned configuration or the existing journal,
never a tool argument. Metadata access is read-only and limited to the approved
company/project/agents. Unknown runs and extra input keys are rejected.

Use distinct dedicated SSH keys for MCP and telemetry/receipt. Each key must
have `restrict` and a fixed command, with no forwarding, PTY or arbitrary remote
command. Use root-owned, non-writable parent directories for authorized_keys.
An unprivileged host account may sudo only its one zero-argument entrypoint.
MCP runs under the coordinator service UID in a hardened transient systemd unit.
Existing operator root access is not the configured MCP transport.

The gateway still has narrowly mediated host privileges to read scoped metadata
and operate verifier resources; it is part of the trusted computing base. This
is not a claim that a compromised gateway is harmless. Its source/config must
remain administrator-owned and changes require review.

Site adapters stay in private deployment configuration. `telemetry_command`
reads bounded JSON on stdin: `probe` returns an allowlisted array of
`id/status/adapterType/active_runs`; `run(issue_id,agent_id,after)` returns null
or one exact `id/status`, after independently enforcing company/project/assignee
and ambiguity checks. `context_command` invokes the trusted `gateway-context`
CLI against the existing journal. `worker_command` invokes `worker_io` with
administrator-owned profile/home/kubeconfig mappings. No adapter may expose raw
agent config, tokens, logs, arbitrary SQL or paths chosen by a model.

Generate the local seccomp profile with `scripts/build_seccomp.py` from an actual
inspected RuntimeDefault OCI profile. Install the resulting profile under the
selected node's kubelet seccomp directory and use a content-addressed filename.
It preserves the default-deny runtime rules and removes socket/network/io_uring
permissions. Select only prepared nodes. See the [Kubernetes seccomp reference](https://kubernetes.io/docs/reference/node/seccomp/).

## Recovery and limits

The receiver never starts models or changes dispatch state on reads. Its timer
can run independently of a chat, but it does not supervise arbitrary work or
send notifications. Ambiguous model writes retain their original quarantine.
Failed/cancelled terminal attempts release their slot only after trusted cleanup
evidence; they retain task claims and do not automatically rotate profiles.
Failed independent tests become `verification_failed`, preserving files and
claims for operator inspection while releasing the already cleaned worker slot.
The receiver's `verifier_seccomp_profile` must match the exact trusted test
evidence; a different or missing policy is never accepted as review-ready.

Verifier Jobs have deterministic names bound to content and policy. After a
disconnect the gateway adopts only matching resources. It caches test evidence
by manifest and policy, and confirms deletion of its Job, pods and ConfigMap.
An operator-positive-control test has a separate label/profile/cache and cannot
be imported as ordinary deny-all evidence.

This release supports top-level small Python artifacts and standard unittest.
The existing worker still performs its original trusted-only unittest step in
its own environment; the new verifier is an additional independent boundary.
Do not expand model-side execution to untrusted repositories on that basis.
Provider renewal, real quota exhaustion/fallback, automatic merges, live model
injection and running-provider cancellation are not enabled. The installed
Paperclip cancellation route is board-only; no durable admin key was added to
work around it. Cancellation remains an operator action followed by receipt of
terminal state and actual cleanup.
